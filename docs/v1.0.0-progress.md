## Phase 3：Experiments（v0.6.0）

### 已完成

**1. 数据模型**

- SQLite migration v3：`experiments` / `experiment_variants` / `experiment_cases` / `experiment_runs`。
- 外键 cascade；删除 experiment 自动删除 children。
- Run 状态：pending / running / succeeded / failed / canceled。

**2. 批量 Runner**

- `internal/experiments`：variant × case 矩阵执行。
- 默认 2 并发；可取消；每个 run 独立失败隔离。
- 每次调用走 Engine；记录 TTFT、耗时、usage、request ID。
- 写入 Inspector：`source=experiment`，记录原始输入、实际 Provider 请求、响应正文。
- 取消时 pending/running 标记 canceled。
- 进程退出时 `Shutdown` 取消所有活跃批次。

**3. Workbench API**

```text
GET    /api/experiments
POST   /api/experiments
GET    /api/experiments/{id}
PUT    /api/experiments/{id}
DELETE /api/experiments/{id}
POST   /api/experiments/{id}/run
POST   /api/experiments/{id}/cancel
GET    /api/experiments/{id}/runs?batch=
GET    /api/experiments/{id}/export?format=json|csv
GET    /api/runs/{id}
PATCH  /api/runs/{id}          # rating 0–5 + note
```

**4. React Experiments 页面**

- 实验列表 + 新建表单。
- Variant：provider / model / system / params（JSON）。
- Case：name / messages（JSON）。
- 运行、停止、删除。
- 结果矩阵：variant × case、状态、输出、thinking、耗时、TTFT。
- 人工评分 0–5 + 备注。
- 导出 JSON / CSV。
- 从 Inspector 请求详情点击 `experiment` 预填一个 case。
- 顶部导航启用 Experiments。

**5. 测试**

- storage：migration v3、experiment CRUD、variant/case 顺序、run 创建/更新/评分/取消、级联删除。
- runner：矩阵执行、全部成功、Inspector 记录、取消、重复启动拒绝。
- workbench：实验创建/列表、运行、轮询完成、评分、非法评分、JSON/CSV 导出、删除。
- 前端：`tsc --noEmit && vite build` 通过。

### 测试结果

```text
$ go vet ./...
$ go test ./...
$ go test -race ./...
$ make build
$ make dist
# 全部通过；二进制约 11 MB；5 平台构建成功
```

### 主要设计决策

1. Runner 使用后台 context，API 立即返回 `202` + `batch_id`；前端轮询 runs。
2. 每轮运行生成新的 run 行，保留历史结果，不覆盖旧批次。
3. 每次 run 独立状态，单个失败不影响其他组合。
4. 评分是人工 0–5，不做统计显著性。
5. 实验调用默认记录正文（单次 capture 覆盖）。
6. 取消同时取消 provider 请求并把未完成 run 标记 canceled。

### 尚未解决的问题

- Provider 配置仍只有 `upstream`（Ollama）。
- Runner 并发固定 2，暂未暴露配置。
- 没有模型 digest 记录；模型更新后无法自动提示结果不可比。
- 没有 LLM-as-Judge、统计显著性、线上分流（按计划不做）。
- 取消后已产生的结果保留；UI 会显示 canceled 状态。
- 实验表单使用 JSON 文本框（params/messages），不是可视化编辑器。
- 未接真实 Ollama 做批量冒烟；发布前建议跑一次 2×2。

### 下一阶段任务（Phase 4）

- 更多 Provider（需真实后端验证后再加）。
- 录制/回放。
- 数据集管理。
- LLM-as-Judge。
- 性能分析、模型能力检测。
- 旧 `/__portal` 合并/重定向。
- v1.0.0 稳定、安装方式、签名、文档收尾。

## Phase 2b：Playground（v0.5.0）

### 已完成

**1. Workbench API**

- `GET /api/providers`：Provider 列表与能力。
- `GET /api/providers/{id}/models`：模型列表。
- `POST /api/chat`：
  - 非流式 JSON；
  - 流式 SSE：`meta` / `delta` / `thinking` / `usage` / `done` / `error`；
  - 支持 provider、model、system、messages、params、think、stream。
- Prompt CRUD：`/api/prompts`、`/api/prompts/{id}`。

**2. Engine 接入**

- main 启动时构造 Ollama Provider（base URL 来自现有 `upstream`）。
- `engine.New` 注册 `ollama`，供 Playground 使用。
- Engine Result 增加 `Prepared` 与 `Provider`，便于记录实际转发请求。

**3. Playground 记录**

- 每次 Playground 调用写入 Inspector：
  - `source=playground`；
  - 记录原始 API 请求、实际 Provider 请求、原始响应；
  - 单次捕获覆盖 `capture_bodies`（Playground 默认记录正文）；
  - 记录 TTFT、耗时、usage、状态。
- 透明代理的正文默认值不受影响。

**4. Prompt 存储**

- SQLite migration v2：`prompts` 表。
- Create / Update / Get / List / Delete。
- Prompt ID 前缀 `prm_`。
- 保存 name / system / messages / params。

**5. React Playground**

- Provider / Model 选择（模型列表 + 手输）。
- System Prompt 编辑器。
- 参数：temperature、top_p、top_k、max_tokens、seed。
- thinking：off / on / passthrough。
- 流式 / 非流式。
- 多轮消息、发送、停止、清空。
- 流式 delta / thinking 渲染。
- TTFT、总耗时、usage、request ID。
- 实际请求 / 原始响应查看。
- “inspect” 跳转 Requests 详情（带异步写入重试）。
- Prompt 保存 / 更新 / 删除 / 加载。
- App 顶部导航：Requests / Playground；Experiments 占位。

**6. 测试**

- Workbench：providers/models、非流式 chat、SSE 流式、参数校验。
- Prompt：创建/列表/更新/删除。
- Playground 捕获：source、system prompt、转发请求、响应正文、usage，即使全局 `capture_bodies=false`。
- storage：migration v2、Prompt CRUD、校验。
- 前端：`npm run build`（tsc + vite）通过。

### 测试结果

```text
$ go vet ./...
$ go test ./...
$ go test -race ./...
$ make build
$ make dist
# 全部通过
```

二进制仍约 11 MB；5 平台构建通过。

### 主要设计决策

1. Playground 走语义 Engine，不复用透明代理路径；两者共享 policy。
2. `POST /api/chat` 的 `think`：
   - `true` → on；
   - `false` → off；
   - 省略/null → passthrough。
3. System Prompt 使用 `override`（编辑器非空时替换已有 system 消息），保证编辑器是权威来源。
4. Playground 正文记录通过单次 capture 覆盖实现，不改变透明代理默认。
5. Prompt 保存在同一 SQLite 数据库，migration v2。
6. SSE done 事件包含 raw response，UI 可直接查看原始响应。

### 尚未解决的问题

- Provider 配置仍只有 `upstream`（Ollama）；`providers` 配置段尚未解析。
- Playground 与透明代理共享上游并发；目前没有独立配额。
- 没有 token 预算/上下文长度检查；超长请求由上游报错。
- Prompt 只保存文本消息，不包含 images/tool calls。
- 没有取消后的部分结果持久化策略：取消会记录错误状态，但保留已收到的正文。
- 未接真实 Ollama 做流式冒烟；发布前建议本地验证一次 thinking on/off、长输出、取消。
- 前端没有组件测试，只有构建 + API/包级测试。

### 下一阶段任务（Phase 3）

- Experiments 数据模型：experiment / variant / case / run。
- 从历史请求创建实验。
- Prompt A/B、多模型、参数组合。
- 批量执行、进度、取消、失败隔离。
- 人工评分与备注。
- 导出 JSON / CSV。
- Replay 与模型 digest 变化提示。

## Phase 2a：Inspector + SQLite（v0.4.0）

### 已完成

**1. SQLite spike**

- 采用 `modernc.org/sqlite v1.40.1`（纯 Go，`CGO_ENABLED=0`）。
- 保持 `go 1.24.0`；未升级到需要 Go 1.25/1.26 的驱动版本。
- 单二进制从约 6.9 MB 增至约 11 MB。
- 5 平台交叉编译通过。

**2. `internal/storage`**

- WAL、`synchronous=NORMAL`、`busy_timeout=5000`、`foreign_keys=ON`。
- 迁移表 + `requests` 表 + 索引。
- Insert / Get / List（元数据）/ Export（完整）/ Delete / DeleteFiltered / Prune / Stats。
- 写入用 mutex 串行化，解决并发 `SQLITE_BUSY`。
- 列表不返回正文；详情和导出才返回。

**3. `internal/inspect` + `internal/inspector`**

- 中立 `Capture` 结构，代理不依赖 SQLite。
- 异步队列（默认 256），`Record` 永不阻塞；队列满丢弃并计数。
- 从请求体提取 model / stream / system prompt。
- 从 OpenAI `usage`、Ollama `prompt_eval_count/eval_count`、SSE/NDJSON 提取 usage。
- TTFT、耗时、状态码、stream。
- 脱敏：精确键名匹配，避免误伤 `max_tokens`。
- 正文上限、截断标记。
- 保留策略：启动和每小时清理。

**4. 代理接入**

- 仅捕获两个 chat 路径。
- 请求原文 + policy 改写后请求。
- 响应体有界 tee，不改变客户端收到的内容。
- 首字节时间记录。
- `CaptureBodyLimit` 默认 256 KiB。
- 透明代理正文默认不落盘。

**5. 工作台 API + UI**

- `/__workbench` 新保留前缀；旧 `/__portal` 保留。
- API：health、stats、requests 列表/详情/删除/导出（JSON/JSONL/CSV）。
- React 19 + TypeScript + Vite 8；`web/dist` 提交并由 `//go:embed` 打包。
- UI：请求列表、筛选、分页、详情四视图、删除、导出、health。
- 仅 loopback；新增 `internal/netutil` 统一 Host/Origin 校验，并回填旧 portal。

**6. 配置与 CLI**

- 新增 `inspector`、`storage` 配置段。
- 新增 `--no-inspector`、`--capture-bodies`、`--db`、`--retention-days`、`--max-rows`。
- 默认：历史开启、正文关闭、保留 14 天 / 5000 条。
- 启动 banner 增加 `/__workbench` URL。
- LaunchAgent 命令包含 db / inspector / thinking / profile 解析结果。
