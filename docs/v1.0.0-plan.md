# LLM Workbench v1.0.0 规划

> 状态：Phase 3 已实施（Experiments），Phase 4 待启动
> 基线日期：2026-11-15
> 当前版本：`0.6.0`（Go）
> 规划范围：从 `ollama-nothink-proxy` 演进为 local-first 的 **LLM Workbench**

---

## 0. 先说结论

### 0.1 前提修正

任务描述假设当前仓库仍是 Python 标准库代理、需要规划 Go 迁移。实际审查结果不是这样：

- `c082c49` 是 Python 0.1.0 实现（`src/ollama_nothink_proxy/__init__.py`，标准库 `http.server`）。
- `1bfb9cb` 已经完成 Go 迁移，删除 Python 源码，新增 `cmd/`、`internal/`、`tests/`、`Makefile`、release workflow。
- 当前 `main` 是纯 Go、**零第三方依赖**、`CGO_ENABLED=0` 可交叉编译的单二进制项目。
- 核心注入逻辑与 Python 版一致；Go 版额外增加了后台守护、控制台、LaunchAgent、双语和更完整的测试。

因此本规划不再重复“Python → Go 迁移”，而是把 **Phase 1 重新定义为“在现有 Go 代理上建立可扩展的 Proxy 基础”**：保留现有行为，补齐 Provider、可配置 thinking、System Prompt、参数策略，并为 Inspector 预留捕获点。

### 0.2 基线验证

2026-11-15 实际执行：

```text
go version go1.27.1 darwin/arm64
go test ./...   # 全部通过
```

模块声明 `go 1.24`，本机工具链 1.27.1，兼容。9 个包通过，`internal/daemon` 无独立测试文件（由 `tests/cli_test.go` 间接覆盖）。

### 0.3 总体策略

采用 **双平面 + 单一策略源**：

1. **兼容平面（Transparent Proxy）**：第三方 Agent / SDK 继续把 base URL 指向本服务，请求按原路径、原格式转发；只在明确配置的策略下改写。
2. **工作台平面（Semantic Workbench）**：Playground、Inspector、Experiments 通过 `/__workbench/api` 调用，由 Provider 负责 API 格式转换，不伪装成透明代理。
3. **单一策略源（Policy）**：参数默认值、thinking 映射、System Prompt 规则只实现一次；`inject`（原始 JSON 改写）与 `provider`（结构化调用）都从同一份描述表派生，禁止出现两套映射。

这是本规划最重要的架构约束。全局规则要求：一旦发现同一职责出现两套实现，必须暂停确认。本项目最容易分叉的地方就是“代理侧 JSON 注入”和“Provider 侧参数映射”，因此第一阶段就把它收敛到 `internal/policy`。

### 0.4 已确认决策

| 决策 | 结论 |
| --- | --- |
| 产品/仓库身份 | **彻底改名**：module path、二进制、配置/日志/数据目录、LaunchAgent label 全部改为 LLM Workbench；提供迁移命令和自动导入，详见 §8.1 |
| 存储 | **`modernc.org/sqlite`**（纯 Go，`CGO_ENABLED=0`）；Phase 2a 前先做跨平台 spike |
| 前端 | **React + TypeScript + Vite**；构建产物嵌入二进制 |
| 正文捕获 | **透明代理默认关闭**；Playground / Experiments 自己发起的调用默认记录正文 |
| 阶段拆分 | **Phase 2a Inspector → Phase 2b Playground** |
| 旧控制台 | v1.0 保留 `/__portal`，新 UI 挂在 `/__workbench` |

“彻底改名”是本规划中唯一明确接受破坏性的变更；其余兼容性契约（API 路径、CLI 参数、配置键、默认注入行为、非 chat 路径透传）仍然必须守住。改名迁移方案见 §8.1。

### 1.2 请求处理链路

实际代码路径：

1. `main.go` 的 `root` handler 先调用 `portal.Handle`。
2. 不是 `/__portal` 前缀则进入 `proxy.Handler.ServeHTTP`。
3. `ServeHTTP`：
   - `validRequestPath` 拒绝非 `/` 开头、`//` 开头、带 host 的 URL；
   - 获取并发信号量（默认 8，等待 2s，超时 503 + `Retry-After: 1`）；
   - `inject.ChatPathKind` 精确匹配 `/v1/chat/completions` 或 `/api/chat`；
   - 对匹配路径读取 body（上限 1 MiB），`DecodeObject` 失败则原样透传；
   - 调用 `InjectV1` / `InjectNative`，重新编码后替换 body；
   - 其余路径不读 body，直接交给 `ReverseProxy`。
4. `ReverseProxy.Rewrite` 只替换 scheme/host/user，保留客户端 path/query；不设置 `X-Forwarded-*`；hop-by-hop 头由 `httputil` 处理。
5. `FlushInterval = 0`，每次写入立即 flush，流式不被缓冲。
6. `statusWriter` 记录状态码和写出字节数，请求结束时写一条结构化日志。

### 1.3 注入语义（当前事实）

| API | thinking | 参数 | 其他 |
| --- | --- | --- | --- |
| `POST /v1/chat/completions` | 无条件写 `reasoning_effort:"none"`；删除 `think` | 仅补客户端缺失的顶层字段 | 保留未知字段和数字原始文本 |
| `POST /api/chat` | 无条件写 `think:false`；删除 `reasoning_effort` | `max_tokens` → `options.num_predict`；`temperature` / `top_p` / `num_ctx` / `repeat_penalty` / `seed` 放进 `options`；其余（如 `keep_alive`）留在顶层 | `options` 不是对象时整包透传，不注入 |

关键代码位置：

- `inject.InjectV1`：`internal/inject/inject.go:49-62`
- `inject.InjectNative`：`internal/inject/inject.go:78-126`
- `nativeOptionKeys`：`internal/inject/inject.go:65-71`
- `proxy.rewriteChat`：`internal/proxy/handler.go:105-154`

**参数优先级（当前）**：客户端 body 显式值永远优先；缺失字段才用注入值。注入值本身的来源优先级为：

```text
内置默认值 < 配置文件 params < PROXY_PARAMS 环境变量 < CLI --set
```

`--no-defaults` 先清空内置默认值。`PROXY_PARAMS` 是整体替换，不是合并；`--set` 是逐项覆盖。

**thinking 的特殊性**：它不是“缺失才补”，而是**无条件强制**。这是本项目存在的原因，也是后续 Playground 想打开 thinking 时最大的兼容性冲突点。

### 1.4 流式、错误与超时

- 流式：`ReverseProxy` + `FlushInterval: 0`，未做任何缓冲；测试用首块到达时间验证。
- 上游错误：状态码和 body 原样透传（400/404/429/500/503 均有测试）。
- 上游不可达：代理返回 502 JSON `{"error":{"message":"proxy: ..."}}`。
- 响应已开始后上游中断：不追加错误 body，只记录日志；客户端看到截断流。
- 超时：`timeoutConn` 对每次 socket read/write 设置 deadline，**不是总请求 deadline**；长流只要持续有数据可以超过 `--timeout`。
- 并发：单一信号量限制所有经过代理的请求；长流会占用槽位。

### 1.5 配置与运行时

- `config.Config` 同时保存启动期只读字段（host/port/log path 等）和运行期可变的 `upstream` / `timeout` / `params` / `lang`，用 `sync.RWMutex` 保护。
- `portal` 保存配置时先原子写文件（temp + rename），成功后才切换内存值；失败不生效。
- `host` / `port` 修改后需要 `restart`，其他即时生效。
- 配置文件是扁平 JSON：`host` / `port` / `upstream` / `timeout` / `params` / `lang`。
- 默认路径（当前；v1.0 改名后的目标路径见 §2.6）：
  - macOS 配置：`~/Library/Application Support/ollama-nothink-proxy/config.json`
  - macOS 日志：`~/Library/Logs/ollama-nothink-proxy.log`
  - 其他系统：`~/.config/...`、`~/.local/state/...`

### 1.6 日志与控制台

- `logstore` 是 100 条环形缓冲 + 每次写入重写整个日志文件。对 100 条足够，但**不适合** Inspector 的请求量；新存储不能复用这个模式。
- 请求日志只有：method、path、status、note（`injected:v1` / `pass` / `busy` 等）、client IP、detail。**没有 body、header、token 用量、耗时字段、请求 ID**。
- `portal` 页面是原生 HTML/CSS/JS，无构建步骤；仅允许 loopback；写接口可改配置、装 LaunchAgent、关机。
- 安全现状：只校验 `RemoteAddr` 是否 loopback；**没有 Origin / Host 校验**。对本地工具可接受，但新增写接口前应补上，防止 DNS rebinding / CSRF。

### 1.7 测试覆盖

已覆盖：

- 注入：V1/Native、强制 thinking、客户端值优先、未知字段与高精度数字保留、非法 `options` 透传。
- 代理：非 chat 路径字节级透传、query/header 透传、上游错误透传、502、HEAD/204/304、body 上限、并发 503、客户端取消释放槽位、流式不缓冲、并发流、上游中途断开。
- CLI：版本、帮助、非法参数退出码、banner、环境变量/配置文件、`--no-defaults`、verbose、日志文件、优雅退出、后台启动/复用/重启、portal 热更新、双语。
- 其他：logstore、i18n、autostart、banner。

### 1.9 审查中发现的具体问题

这些不是“顺手重构”，而是会直接影响新功能的点：

1. **`top_k` 落错位置**：`nativeOptionKeys` 不含 `top_k`，`--set top_k=40` 会被放到 `/api/chat` 顶层，Ollama 不认。新参数管理必须补齐 Native option 描述表（`top_k`、`min_p`、`typical_p`、`presence_penalty`、`frequency_penalty`、`stop`、`num_keep` 等）。
2. **`reasoning_effort:"none"` 是 Ollama 方言**：如果未来 upstream 换成 LM Studio / llama.cpp 的 OpenAI 兼容层，这个字段可能被忽略或拒绝。Provider 必须把“thinking 能力”和“控制字段”分开描述。
3. **默认参数含 `max_tokens:96`**：这是原项目的“防跑飞”设计。Playground 如果直接复用会把输出截得很短；必须让 Playground 使用独立参数集，不能误用代理默认值。
4. **日志文件每次请求全量重写**：100 条尚可，Inspector 不能沿用。
5. **没有请求 ID**：无法把“代理日志”“Playground 请求”“Inspector 详情”关联起来。
6. **`/__portal` 是唯一保留前缀**：新的 UI 不能挂在 `/`，否则会破坏透明代理。必须新增保留前缀。
7. **配置 `Apply` 会重写整个文档**：新增配置键后，保存路径必须保留未知键，否则新旧版本混用会丢配置。
8. **`timeout` 是每 socket 操作超时**：Provider 的流式读取要沿用这个语义，不要误写成总 deadline。
9. **portal 无 Origin/Host 校验**：新增写接口前必须补，且建议回填到旧 portal。

## 2. 目标架构设计

### 2.1 设计约束

必须同时满足：

- Proxy 可以独立运行，不依赖 Web UI / SQLite；关闭 Inspector 后行为与现在一致。
- 第三方 Agent 继续使用原 base URL 和原 API；默认行为不变。
- 所有数据默认本地；不引入云服务、不遥测。
- 只有一个策略源；Provider 只负责“怎么和某个 runtime 说话”。
- 不为未验证的 Provider 提前做复杂抽象；第一阶段只有 Ollama。
- 单个可执行文件；`CGO_ENABLED=0` 交叉编译不能破。

### 2.2 两个平面

```text
第三方 Agent / SDK
        │  OpenAI 或 Ollama 原生协议
        ▼
┌──────────────────────────────────────────────────────────────┐
│ 兼容平面：transparent proxy                                  │
│  - 路径/格式/错误码/流式语义尽量原样                          │
│  - policy.ApplyRawV1 / ApplyRawNative（原 inject）            │
│  - inspector 旁路捕获（有界、异步、可关闭）                   │
└───────────────────────────┬──────────────────────────────────┘
                            │
                            ▼
                     Ollama / 未来 Provider

浏览器
  │  /__workbench  （React SPA + JSON/SSE API）
  ▼
┌──────────────────────────────────────────────────────────────┐
│ 工作台平面：server/workbench                                 │
│  - playground：语义调用、流式展示、参数编辑                    │
│  - inspector：历史查询、详情、导出、删除                       │
│  - experiments：A/B、批量、评分、导出                          │
│         │                                                    │
│         ▼                                                    │
│  engine：策略 → Provider → 事件流 → 记录                       │
└───────────────────────────┬──────────────────────────────────┘
                            │
                     ┌──────▼──────┐
                     │  SQLite     │
                     │ (仅工作台)   │
                     └─────────────┘
```

**为什么不在 `/v1/chat/completions` 上做 Playground？**

因为透明代理必须保持请求/响应的原始语义，而 Playground 需要解析流、计算 TTFT、展示 usage、注入 System Prompt、保存实验快照。把这些塞进代理路径会让兼容面变复杂。正确做法是：Playground 走自己的 API，使用 Provider 的语义接口；它产生的请求同样写入 Inspector。

### 2.3 模块边界（目标）

```text
cmd/
  llm-workbench/              # v1.0 起正式二进制名
internal/
  config/                     # 配置解析 + 新 schema；保留旧键兼容
  server/                     # HTTP 路由、loopback/Host/Origin 守卫、生命周期
  proxy/                      # 透明代理（尽量不改核心）
  policy/                     # ★ 单一策略源：参数描述、thinking、system prompt
  inject/                     # 兼容薄层：policy 的 Raw JSON 适配器
  provider/                   # Provider 接口、模型/能力/错误类型
    ollama/                   # 第一阶段唯一实现
  engine/                     # 语义调用编排：策略 → provider → 事件/usage
  inspector/                  # 捕获、脱敏、TTFT、异步落库
  storage/                    # SQLite、迁移、查询、保留策略
  workbench/                  # /__workbench API + 静态资源
  experiments/                # 第二阶段后半段
  portal/                     # 旧控制台，保留
  logstore/ i18n/ daemon/ autostart/   # 保留
web/                          # React + TS + Vite 源码与构建产物
docs/
```

原则：

- `policy` 不依赖 `provider`，也不依赖 `proxy`；它是纯逻辑。
- `provider` 不读全局配置，不决定默认参数；只接收已解析的 `ChatRequest` 并做 wire mapping。
- `engine` 负责把 UI 请求 + 配置 + profile 合并成最终 `ChatRequest`，再交给 provider。
- `inspector` 通过接口接收快照，不直接依赖 `http` 或 `sqlite`。
- `proxy` 不依赖 `storage`；只依赖一个 `Recorder` / `Capture` 接口。

### 2.4 参数与优先级（核心契约）

#### 2.4.1 透明代理的采样参数

从高到低：

1. **客户端 body 显式字段**（永远不被覆盖）。
2. **请求级 profile**（`X-Workbench-Profile: <name>`，完整快照）。
3. **启动时选中的 profile / 全局 params**：
   - CLI `--set`
   - 环境变量 `PROXY_PARAMS`
   - 配置文件 `params`
   - 内置默认 profile（`nothink`，与当前一致）
4. Provider 自身的服务端默认值（代理不干预）。

说明：`--set` 会覆盖启动时选中的 profile 参数；请求头选择的 profile 是独立快照，不叠加全局 `--set`。这样既不破坏现有配置语义，也不会让显式 CLI 参数静默失效。

**thinking 不适用“客户端显式值永远优先”**：它是策略（`off` / `on` / `passthrough`），默认 `off` 会强制关闭，这是原产品的核心行为。客户端想打开必须显式切换模式或使用 `on` / `passthrough` profile，不能只靠传 `think:true` 或 `reasoning_effort:"high"` 绕过默认策略。否则“默认关闭思考”的兼容承诺就不成立。

#### 2.4.2 thinking

thinking 不是“缺失才补”，而是策略模式：

| 模式 | `/v1/chat/completions` | `/api/chat` |
| --- | --- | --- |
| `off`（默认） | 强制 `reasoning_effort:"none"`，删除 `think` | 强制 `think:false`，删除 `reasoning_effort` |
| `on` | 不再强制 `none`；保留客户端已有的 `reasoning_effort`；删除 `think` | 强制 `think:true`，删除 `reasoning_effort` |
| `passthrough` | 不碰 `reasoning_effort` / `think` | 不碰 `think` / `reasoning_effort` |

`on` 的语义是“停止强制关闭”，不擅自写一个具体的 reasoning level。具体 level（low/medium/high）由客户端显式传；Provider 能力描述会说明是否支持。这样对 Ollama 版本差异最稳。

#### 2.4.3 System Prompt

| 模式 | 行为 |
| --- | --- |
| `off`（默认） | 完全不碰 messages |
| `inject-if-missing` | 若 messages 中没有 `system` / `developer` 消息，则在最前面插入一条；已有则保持原样 |
| `override` | 删除所有 `system` / `developer` 消息，在最前面插入配置的 system 消息 |

约束：

- 只改 messages 数组，其他字段保持 `json.RawMessage` 原样。
- `messages` 缺失或不是数组时**不注入**，按原样透传，并在日志 note 中标记。
- System Prompt 可能让请求超出上下文；代理不做静默截断，只透传上游错误。
- `override` 是破坏性操作，必须显式开启，不能作为默认。

#### 2.4.4 请求级控制头

只接受 `X-Workbench-*` 命名空间，并在转发前删除：

- `X-Workbench-Profile: nothink|raw|<custom>`
- `X-Workbench-Thinking: off|on|passthrough`
- `X-Workbench-System-Prompt: <text>`（可选；更长文本用 profile 配置）

未知 profile 返回 400 JSON 错误（不静默忽略，避免用户以为生效了）。非 chat 路径不解析这些头，直接透传（并继续删除？不，非 chat 路径保持原样，包括头；只有 chat 路径消费并删除）。

### 2.5 Provider 设计

第一阶段只实现 Ollama，接口保持最小：

```go
type Provider interface {
    ID() string
    Name() string
    Capabilities() Capabilities
    ListModels(ctx context.Context) ([]Model, error)
    Chat(ctx context.Context, req ChatRequest) (ChatResponse, error)
    ChatStream(ctx context.Context, req ChatRequest, emit func(Event) error) (ChatResponse, error)
}

type Capabilities struct {
    Streaming       bool
    Thinking        ThinkingSupport // none | bool | levels
    Usage           bool
    SystemRole      bool
    ToolCalls       bool
    SamplingParams  []string        // 规范化参数名
}

type ChatRequest struct {
    Model    string
    Messages []Message
    Params   map[string]json.RawMessage // 已由 policy 合并
    Think    *bool                      // nil = 不指定
}

type ChatResponse struct {
    Text       string
    Thinking   string
    Usage      *Usage
    Finish     string
    Raw        json.RawMessage // 上游原始响应（非流式为完整 body；流式为聚合后的原始帧，受上限约束）
    Model      string
    ModelDigest string         // Ollama /api/show 可得时记录
}
```

Ollama Provider：

- 模型列表：`GET /api/tags`。
- 对话：`POST /api/chat`，`stream:false` 或 `true`。
- 流式解析：NDJSON，逐行 `json.Unmarshal`；兼容空行；单行上限（如 1 MiB）防止异常上游撑爆内存。
- 提取：`message.content`、`message.thinking`、`done`、`done_reason`、`prompt_eval_count`、`eval_count`、`total_duration`、`load_duration`、`prompt_eval_duration`、`eval_duration`。
- thinking：`think:false` / `true`；未来若 Ollama 支持 level，通过 `Capabilities.Thinking` 描述，不在接口里硬编码。
- 错误：非 2xx 读取有界 body，返回 `*provider.HTTPError{Status, Body}`；不自动重试。
- 取消：全部使用 `ctx`；客户端断开时取消上游请求。

**不做的抽象**（明确非目标）：

- 不做动态插件、注册中心、gRPC、统一多模态。
- 不为 llama.cpp / LM Studio / MLX 提前写空实现。
- 不把 Provider 做成“能表达所有厂商差异”的大接口；第二阶段只加一个 OpenAI-compatible 实现，用真实后端验证。

SQLite 配置：

- `journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`、`foreign_keys=ON`。
- 写入串行化：单个 writer goroutine；读取走独立连接。
- 迁移用嵌入的 SQL + `schema_migrations`，启动时自动执行；失败则拒绝启动工作台（代理仍可运行）。
- 保留策略：按天数 + 行数 + 总字节三重上限，后台低频清理；默认建议 14 天 / 5000 条 / 512 MiB（可配置）。
- 不在请求路径同步写库；异步队列满时丢弃并计数，绝不阻塞流。

### 2.7 Inspector 捕获设计

捕获范围：

- 透明代理：只捕获 `/v1/chat/completions` 和 `/api/chat`（未来可配置扩展到 `/v1/completions` 等）。
- 工作台：Playground / Experiments 的所有模型调用。
- 不捕获 `/__portal`、`/__workbench` 的配置/查询请求。

记录内容：

- 请求 ID、时间、来源、provider、model、endpoint、method、stream。
- 原始请求（客户端发来的，脱敏）与实际转发请求（policy 改写后，脱敏）。
- 响应状态、错误、耗时、TTFT、usage、响应 body（有界）。
- 上游响应头：默认只存 allowlist（`content-type`、`content-length`、`x-request-id`），不存 `set-cookie` 等。

TTFT 定义：

- 透明代理：从进入 handler 到第一次向客户端写出响应 body 的时间。
- 工作台：从发起 Provider 请求到第一个 `delta` / `thinking` 事件的时间。
- 非流式：等于总耗时（或首字节时间），UI 标注为“非流式”。

捕获实现要点：

- 请求侧：`rewriteChat` 已经有 `data` 和 `encoded`，直接传给 capture；非 chat 路径不抓 body。
- 响应侧：用包装的 `ResponseWriter`，`Write` 时追加到有界 buffer，同时立即写客户端并 flush；`Unwrap` 保持 `http.ResponseController` 可用。
- 流式：不解析也能先存原始 SSE/NDJSON 片段；结束时再解析文本/usage。解析失败不影响透传。
- 上限：单字段建议 256 KiB；流式响应上限 1 MiB；超过则截断并标记 `response_truncated=1`。
- 脱敏：在落库前做，不能在展示层才做；导出同样脱敏。
- 关闭：`inspector.capture_bodies=false` 时只记元数据；`inspector.enabled=false` 时完全不记（代理零额外开销）。

脱敏规则：

- 请求头：默认不存；若开启，只存 allowlist，永不存 `Authorization`、`Cookie`、`Proxy-Authorization`、`X-Api-Key`。
- Query：`key`、`api_key`、`token`、`access_token`、`authorization` 等值替换为 `[REDACTED]`。
- JSON body：只对**键名**匹配 `api_key` / `apikey` / `token` / `password` / `secret` / `authorization` 的值脱敏，不改写 prompt 正文。
- 配置中的 provider key 不进入日志；错误信息如果包含 URL，保留 URL 但去掉 userinfo 和敏感 query。

### 2.8 Playground / Workbench API

所有路由挂在 `/__workbench`，仅 loopback：

```text
GET    /__workbench/                          SPA
GET    /__workbench/api/health                版本、provider、存储状态
GET    /__workbench/api/providers             列表与能力
GET    /__workbench/api/providers/{id}/models 模型列表
POST   /__workbench/api/chat                  流式 / 非流式
GET    /__workbench/api/requests              列表 + 筛选 + 分页
GET    /__workbench/api/requests/{id}         详情（原始/转发/响应/计时）
DELETE /__workbench/api/requests/{id}
DELETE /__workbench/api/requests              按条件清空
GET    /__workbench/api/requests/{id}/export  单条导出
GET    /__workbench/api/requests/export       批量导出
GET/POST/PUT/DELETE /__workbench/api/prompts  Prompt 保存/加载
GET    /__workbench/api/settings              只读运行配置（脱敏）
POST   /__workbench/api/settings              可写的运行配置
```

`POST /api/chat` 请求体：

```json
{
  "provider": "ollama",
  "model": "qwen3:8b",
  "system": "You are a helpful assistant.",
  "messages": [{"role": "user", "content": "hi"}],
  "params": {"temperature": 0.7, "top_p": 0.9, "num_predict": 512},
  "think": false,
  "stream": true,
  "save": true,
  "prompt_id": null
}
```

流式响应使用 SSE：

```text
event: meta
data: {"request_id":"req_...","provider":"ollama","model":"qwen3:8b"}

event: delta
data: {"text":"Hello"}

event: thinking
data: {"text":"..."}

event: usage
data: {"prompt_tokens":10,"completion_tokens":20,"total_tokens":30}

event: done
data: {"finish_reason":"stop","duration_ms":1234,"ttft_ms":210}

event: error
data: {"message":"...","status":500}
```

取消：客户端断开 SSE 连接即取消上游请求（`r.Context()`）。

安全：

- 仅 loopback（复用现有 `isLoopback`）。
- 写接口校验 `Origin`（缺失或同源才允许）和 `Host`（`127.0.0.1` / `localhost` / `[::1]` / 配置的监听地址）。
- 不设置 CORS；开发时用 Vite proxy，不放开跨域。
- `provider` 只允许配置中存在的 ID，禁止请求里传任意 base URL（避免 SSRF）。
- 不把请求转发到非配置上游。

- 默认只监听 `127.0.0.1`。

   - 兼容别名：`ONP_LANG` 继续作为 `LLM_WORKBENCH_LANG` 的兼容别名；`PORT` / `UPSTREAM` / `PROXY_PARAMS` 保持不变。
   - 明确不做旧二进制名双发；v0.3.0 发布说明标注“仅名称/路径变更，API 与默认行为不变”。
   - 仓库在 GitHub 上改名后，旧 URL 由 GitHub 重定向； Homebrew formula、文档链接同步更新。
2. **建立 `internal/policy`**
   - 参数描述表：canonical name、OpenAI 字段、Ollama option、类型、默认值、适用 API。
   - thinking 映射：`off` / `on` / `passthrough` × 两种 API。
   - system prompt 映射：`off` / `inject-if-missing` / `override`。
   - `inject` 改为调用 policy，保留 `InjectV1` / `InjectNative` 签名和现有测试。
   - 补齐 Native option：`top_k`、`min_p`、`typical_p`、`presence_penalty`、`frequency_penalty`、`stop`、`num_keep` 等（具体以 Ollama 文档为准，逐项测试）。
3. **配置扩展（向后兼容）**
   - 新增 `profiles`、`thinking`、`system_prompt`、`inspector`（本阶段仅解析/校验，不落库）、`providers`（Ollama）。
   - 默认值必须复现当前行为：`thinking=off`、`params` 为内置四项、system prompt off。
   - `--thinking`、`--system-prompt`、`--system-prompt-file`、`--profile` 等 CLI 参数（按需，避免爆炸）。
   - `Config.Apply` 保留未知键，避免旧版本/旧 portal 保存时丢新配置。
4. **Provider 最小实现**
   - `provider.Provider` 接口、`Capabilities`、`Model`、`Usage`、`HTTPError`。
   - `provider/ollama`：`/api/tags`、`/api/chat` 非流式 + NDJSON 流式、thinking、usage、取消、错误透传。
   - 用 `httptest` 假上游做完整单测；不接真实 Ollama 的测试也要能跑。
5. **Engine 雏形**
   - `engine.Chat` / `engine.ChatStream`：合并配置 + profile + 请求参数，调用 provider，产出事件。
   - 本阶段不暴露 HTTP 路由；用单测覆盖。这样 Phase 2 接 UI 时不用再改 Provider。
6. **请求 ID**
   - 内部生成 `req_...`；透明代理默认**不**加响应头（保持原样），只在 Inspector 开启时内部关联。
   - 工作台 API 在 SSE `meta` / JSON 中返回。
7. **文档**
   - README 重新定位（LLM Workbench，但说明仍是 Ollama-first）。
   - `docs/proxy-config.md`、`docs/providers.md`、`docs/migration.md`。
   - 迁移说明：旧配置、旧 CLI、旧 API 不变；名称/路径变化与 `migrate` 用法。

明确不做：

- 不做 UI。
- 不做 SQLite。
- 不做 Experiments。
- 不添加第二个 Provider。
- 不改默认注入行为。

测试：

- 现有全部测试必须原样通过（路径/名称相关断言同步更新）。
- 改名迁移：旧配置导入、旧配置不存在、新旧都存在、`migrate` 幂等、旧 plist 检测、`ONP_LANG` 兼容别名。
- 新增 golden compatibility：默认 profile 下，V1/Native 的转发 body 与当前逐字节一致（除允许的字段顺序差异；用 JSON 语义比较 + 关键字段原始文本比较）。
- thinking 矩阵：3 模式 × 2 API × 客户端是否已带字段。
- system prompt 矩阵：3 模式 × 有/无 system × 非法 messages。
- 参数映射：OpenAI 顶层 / Ollama options / 未知字段保留。
- Provider：流式分块、空行、非法 JSON、上游 4xx/5xx、超时、取消、usage、thinking。
- `go test -race ./...`、`go vet ./...`、`go build ./...`。

退出标准：

## 5. 技术选型及依赖分析

### 5.1 后端

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | Go（保持） | 已迁移完成；单二进制、并发、HTTP/JSON 足够 |
| HTTP | 标准库 `net/http` + `httputil.ReverseProxy` | 现有实现稳定；不引入框架 |
| 路由 | Go 1.22+ `ServeMux` 模式或现有手动分发 | 路由数量少；避免第三方 router |
| JSON | `encoding/json` + `json.RawMessage` | 保留未知字段和数字原始文本；现有测试依赖 |
| 流式 | `Flusher` / `http.ResponseController` | 现有已验证 |
| 日志 | 标准库 `log` + 自有结构化存储 | 不引入日志框架 |
| 配置 | 现有 JSON + 校验 | 不引入 viper |
| 测试 | `testing` + `httptest` | 现有风格 |

### 5.2 SQLite 驱动

已确认使用 `modernc.org/sqlite` + `database/sql`。

| 方案 | CGO | 交叉编译 | 二进制增量 | 成熟度 | 结论 |
| --- | --- | --- | --- | --- | --- |
| `modernc.org/sqlite` | 否 | 好 | 较大（约 10–20 MB 量级，需实测） | 高 | **采用** |
| `github.com/ncruces/go-sqlite3` | 否（WASM） | 好 | 中等 | 较高 | 备选 |
| `github.com/mattn/go-sqlite3` | 是 | 差（需各平台 C 工具链） | 小 | 最高 | 不采用，破坏现有 release 矩阵 |
| 自写 JSONL 存储 | — | — | 无 | 低（查询/并发/事务要自己做） | 仅在 spike 失败时重新确认 |
| 纯内存 + 文件导出 | — | — | 无 | 低 | 不满足历史/筛选需求 |

代价：

- 打破“零第三方依赖”。
- 二进制变大。
- 需要验证 5 平台交叉编译（`CGO_ENABLED=0` 下应该可行）。
- 首次编译变慢。
- 驱动版本必须与 `go.mod` 的 Go 版本兼容；若最新版要求更高 Go，需评估提升 `go` 指令并同步 CI/release。

缓解：

- 存储放在 `internal/storage`，接口化；测试用临时文件。
- CI 增加 5 平台 `go build`（已有 release workflow，补 Step）。
- 在 Phase 2a 开始前先做一个 spike：只加驱动 + 打开/迁移/写入 benchmark，确认二进制大小和交叉编译，再决定是否继续。
- 如果 spike 失败，回退到 JSONL + 内存索引，并把 Inspector 的筛选能力降级；这需要重新确认范围。

实施结果（Phase 2a）：

- `modernc.org/sqlite v1.40.1`，`go 1.24.0`；
- 单二进制约 11 MB（引入前约 6.9 MB）；
- 5 平台 `make dist` 通过；
- 写入串行化（mutex）解决并发 `SQLITE_BUSY`。

### 5.3 前端

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | React + TypeScript | 任务推荐；生态成熟；组件化适合 Inspector |
| 构建 | Vite | 快、配置少 |
| 样式 | 原生 CSS / CSS Modules | 不引入 Tailwind/组件库，保持轻量 |
| 状态 | React 内置 + 少量自定义 hooks | 不引入 Redux/Zustand |
| 流式 | `fetch` + `ReadableStream` 解析 SSE | 比 `EventSource` 更可控（支持 POST、取消） |
| 路由 | 轻量客户端路由或 `react-router`（按需） | 页面少；避免过度依赖 |
| 测试 | Vitest（可选）+ Playwright 冒烟（可选） | 先把 API 测试做扎实 |

构建与嵌入：

- 已确认使用 React + TypeScript + Vite。
- `web/dist` 通过 `//go:embed` 嵌入 `internal/workbench`。
- `make build` 先 `npm ci && npm run build`，再 `go build`。
- release workflow 增加 Node setup 和前端构建。
- **提交 `web/dist`**：保证裸 `go build` / `go install` 可用；CI 执行 `npm run build` 后校验 `git diff --exit-code web/dist`，防止产物与源码不一致。
- `web/node_modules` 不提交；`package-lock.json` 提交。
- Node 版本固定为 22 LTS（`.nvmrc` / CI `setup-node`），Vite 与插件版本锁定。

替代方案：继续用原生 HTML/JS 扩展 `portal.html`。已确认不采用；旧 portal 只在 v1.0 保留，不再扩展。

### 5.4 依赖预算

目标：后端新增依赖不超过 SQLite 驱动及其必要传递依赖；前端依赖只用于构建，不进运行时。

| 依赖 | 阶段 | 必要性 | 备注 |
| --- | --- | --- | --- |
| `modernc.org/sqlite` | Phase 2a | 高 | 唯一后端第三方依赖 |
| React / ReactDOM | Phase 2b | 高 | 构建期；打包进静态资源 |
| Vite / TypeScript | Phase 2b | 高 | 构建期 |
| `react-router` | Phase 2b | 低 | 页面少可不用 |
| 组件库 | — | 不需要 | 保持轻量 |
| ORM | — | 不需要 | `database/sql` 足够 |
| 日志/配置框架 | — | 不需要 | 标准库 |

### 5.5 构建与发布

- 继续 `CGO_ENABLED=0`、`-trimpath`、`-ldflags="-s -w"`。
- `make build`：前端构建 + Go 构建。
- `make test`：`go test ./...`；新增 `make test-race`、`make test-provider`（可选）。
- release workflow：新增 Node 22 + `npm ci && npm run build`；产物名改为 `llm-workbench_<version>_<os>_<arch>`。
- release matrix 不变：darwin arm64/amd64、windows amd64、linux amd64/arm64。
- 先在 CI 增加 SQLite spike 的交叉编译，再合并 Phase 2a。

## 6. 主要技术风险与兼容性风险

### 6.1 高风险

| # | 风险 | 影响 | 触发条件 | 缓解 |
| --- | --- | --- | --- | --- |
| 1 | **默认行为漂移** | 现有用户升级后 thinking 打开、输出变长/变慢、参数被改 | 重构 `inject` 时改变默认 profile | 默认 `nothink` 必须逐字节复现；golden 测试；发布说明显式标注 |
| 2 | **两套参数映射分叉** | 代理注入与 Playground 行为不一致，难以排查 | `inject` 和 `provider` 各自维护一份字段表 | 单一 `policy` 描述表；代码审查把“第二份映射”作为阻塞问题；发现即暂停 |
| 3 | **SQLite 依赖破坏构建** | 交叉编译失败、二进制暴涨、release 失败 | 选错驱动或 CGO | Phase 2a 前 spike；只用纯 Go 驱动；CI 全平台构建 |
| 4 | **正文捕获泄露敏感信息** | Prompt/密钥落盘，违反隐私预期 | 默认开启正文且脱敏不完整 | 代理侧默认关闭，显式开启；脱敏在落库前；可关闭；保留期限；文档明确 |
| 5 | **流式捕获拖慢首 token** | 代理的核心优势（低延迟）被破坏 | 同步写库/同步解析 | 有界内存 + 异步队列；写库不阻塞；首块延迟测试 |
| 6 | **UI 挂载路径冲突** | 破坏透明代理 | 把 SPA 挂在 `/` | 只用 `/__workbench`；文档列出保留前缀 |
| 7 | **彻底改名破坏兼容** | 旧配置/LaunchAgent/Homebrew/脚本失效 | 改 module path、二进制名、目录 | 独立改名提交；`migrate` 自动导入旧配置；旧 plist 只提示不静默操作；发布说明标注 breaking；API/CLI 参数/配置键不变 |

| # | 风险 | 影响 | 缓解 |

| 8 | Ollama 版本差异（`reasoning_effort`、`think` level） | thinking 控制不生效或请求被拒 | 能力描述 + 保守映射；`on` 只停止强制关闭；错误原样透传；文档标注版本 |

### 6.3 兼容性契约（必须守住）

1. 旧 CLI 参数、环境变量、配置文件键继续可用；默认值不变；名称/路径变化由 `migrate` 处理。
2. 旧 API 路径 `/v1/chat/completions`、`/api/chat` 的行为在默认 profile 下不变。
3. 非 chat 路径字节级透传（body、query、header、状态码、流式）。
4. 上游错误状态码和 body 不被包装（代理自身错误除外）。
5. `/__portal` 继续可用；旧书签不失效。
6. 单二进制、`CGO_ENABLED=0` 交叉编译不破。
7. 日志默认不含凭据；透明代理正文捕获默认关闭。
8. 旧配置在首次启动/`migrate` 时导入，原文件保留；升级本身不改写旧文件。
9. 旧二进制名不再发布；这是已确认的 breaking change，发布说明必须显著标注，API/默认行为不受影响。

### 6.4 需要立即暂停并确认的情况

按仓库全局规则，出现以下任一情况必须停下来确认，不得自行绕过：

- `inject` 与 Provider 出现第二套参数/thinking 映射。
- 需要修改透明代理的默认语义才能实现新功能。
- 需要改变旧配置键的含义，或旧录像/计划/协议兼容性受影响。
- SQLite spike 失败，需要换存储方案。
- 前端方案导致 `go build` 无法独立完成单二进制。
- 计划与代码不一致，或验收标准出现歧义。

## 7. 测试矩阵与验收

### 7.1 兼容性

- 默认 profile 下，V1/Native 转发 body 与 0.2.0 一致。
- 非 chat 路径（`/api/tags`、`/api/show`、`/api/pull`、`/v1/models` 等）字节级透传。
- 客户端显式参数永远不被默认值覆盖。
- 上游 400/404/429/500/503 状态码和 body 透传。
- HEAD/204/304、query、header、hop-by-hop 处理不变。
- 流式首块不被缓冲；并发流完整。
- 客户端取消释放槽位；上游中途断开不崩。
- 旧 portal、旧 CLI、旧配置继续工作。

### 7.2 新功能

| 领域 | 用例 |
| --- | --- |
| thinking | off/on/passthrough × V1/Native × 客户端已带/未带字段 |
| system prompt | off/inject-if-missing/override；有/无 system；多 system；非法 messages |
| 参数 | OpenAI 顶层、Ollama options、`max_tokens→num_predict`、`top_k` 等、未知字段保留、数字原文 |
| Provider | 模型列表、非流式、NDJSON 流、usage、thinking、4xx/5xx、超时、取消、畸形行 |
| Inspector | 捕获、TTFT、截断、脱敏、异步、关闭、删除、筛选、导出 |
| SQLite | 迁移幂等、并发、WAL、保留、损坏降级 |
| Workbench API | 参数校验、SSE 格式、取消、Provider/模型不存在、Origin/Host |
| Experiments | 变体×用例、部分失败、取消、评分、Replay、导出 |
| 安全 | Authorization/Cookie 不入库；query 脱敏；JSON 敏感键脱敏；loopback 限制；Host/Origin |

### 7.3 非功能

- `go test -race ./...` 全绿。
- `go vet ./...` 全绿。
- 5 平台 `CGO_ENABLED=0` 构建。
- 代理开启 Inspector 后首 token 延迟无可感知退化（测试阈值 + 手动对比）。
- 100 并发流不崩、不泄漏 goroutine（可用 `goleak` 仅测试依赖，或手工 pprof）。
- 数据库 10k 条记录下列表查询可接受（目标 < 100ms，本地）。

### 7.4 每阶段验收

每个阶段结束必须更新 `docs/v1.0.0-progress.md`：

- 已完成内容。
- 主要设计决策（与本文的差异）。
- 测试结果（命令 + 输出摘要）。
- 尚未解决的问题。
- 下一阶段任务。
- 兼容性检查结论。

## 8. 已确认决策与改名迁移

### 8.1 彻底改名方案

新身份：

| 项 | 新值 |
| --- | --- |
| 产品名 | LLM Workbench |
| module path | `github.com/jachy-h/llm-workbench` |
| 二进制 | `llm-workbench` |
| GitHub 仓库 | `llm-workbench`（由 GitHub 重定向旧 URL） |
| 配置目录 | macOS `~/Library/Application Support/llm-workbench/`；Linux `$XDG_CONFIG_HOME/llm-workbench/` |
| 日志 | macOS `~/Library/Logs/llm-workbench.log`；Linux `$XDG_STATE_HOME/llm-workbench/` |
| 数据 | `workbench.db`，位于 §2.6 的数据目录 |
| LaunchAgent label | `com.github.llm-workbench` |

实施时点：**Phase 1 第一个独立提交**，随 `v0.3.0` 发布。这是 pre-1.0 的 breaking change，只影响名称/路径，不影响 API、CLI 参数、配置键和默认代理行为。

迁移设计：

1. **`llm-workbench migrate` 命令（显式）**
   - 检测旧配置：macOS `~/Library/Application Support/ollama-nothink-proxy/config.json`；Linux `~/.config/ollama-nothink-proxy/config.json`。
   - 新配置不存在时复制旧配置到新路径；已存在时不覆盖，只报告差异。
   - 不删除旧配置、旧日志。
   - 检测旧 LaunchAgent（`com.github.ollama-nothink-proxy`），打印卸载/重装命令；不静默操作 launchd。
   - 幂等：重复执行安全。
2. **首次启动自动导入（保守）**
   - 新配置不存在且旧配置存在时，读取旧配置作为启动值，并在首次保存时写入新路径；旧文件保留。
   - 这样老用户直接运行新二进制不会丢配置。
3. **环境变量兼容**
   - 新增 `LLM_WORKBENCH_LANG`；`ONP_LANG` 继续作为别名，优先级低于新变量。
   - `PORT`、`UPSTREAM`、`PROXY_PARAMS` 保持不变。
4. **CLI / API 兼容**
   - 子命令 `serve` / `start` / `restart` 保持不变，新增 `migrate`。
   - 所有现有 flag 保持不变；新增 flag 只增不改。
   - `/v1/chat/completions`、`/api/chat`、`/__portal` 不变。
5. **发布与文档**
   - release 产物名改为 `llm-workbench_<version>_<os>_<arch>`。
   - README、Homebrew formula、下载链接、LaunchAgent 贡献文件同步改名。
   - `docs/migration.md` 写明：旧二进制名不再发布；脚本需改路径；API 不变；如何回滚（旧二进制 + 旧配置仍可用）。
6. **回滚**
   - 旧二进制仍可读取旧配置；新配置独立，不破坏回滚。
   - 新数据库不回写旧格式；回滚后 Inspector 数据不可见，但代理功能不受影响。

不采用：

- 不长期双发旧二进制名。
- 不在旧路径继续写配置。
- 不自动删除旧 LaunchAgent 或旧日志。

### 8.2 其他已确认决策

| 决策 | 结论 |
| --- | --- |
| SQLite | `modernc.org/sqlite` + `database/sql`；Phase 2a 前做 5 平台 spike |
| 前端 | React + TypeScript + Vite；提交 `web/dist`，CI 校验 |
| 透明代理正文捕获 | 默认关闭；Playground/Experiments 自己发起的调用默认记录 |
| Phase 2 | 拆成 2a Inspector / 2b Playground |
| 旧控制台 | v1.0 保留 `/__portal`；新 UI 在 `/__workbench` |

### 8.3 实施中仍需确认的开放问题

这些不阻塞 Phase 1，但必须在对应阶段开始前定下来：

- SQLite spike 后的二进制增量是否可接受；若不可接受，是否重新评估 `ncruces` 或 JSONL。
- Playground/Experiments 与第三方 Agent 的上游并发配额：共享信号量还是独立配额。
- 透明代理是否要在响应头暴露 request ID：默认倾向不暴露，保持响应头原样。
- 旧 `/__portal` 何时并入新 Settings；v1.0 只保留，不迁移。
- 是否提供 `llm-workbench export` CLI；Phase 2a 先做 API/UI 导出，CLI 视需求再加。

## 11. 一句话总结

先把现有 Go 代理的**行为契约**锁死，把参数/thinking/System Prompt 收敛成**一套策略**，用最小 Ollama Provider 打通语义调用；然后按 Inspector → Playground → Experiments 的顺序增量交付。SQLite 和 React 是手段，不是目的；任何会改变默认代理行为或引入第二套映射的改动，都先停下来确认。
